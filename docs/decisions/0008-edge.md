# 0008. The edge: how traffic reaches the services, and with which certificates

- **Status:** accepted: nginx through the NixOS module with the NixOS ACME module; one domain with CNAMEs; the split public / VPN-only; the DNS challenge by CNAME delegation to a public acme-dns
- **Date:** 2026-10-01
- **Phase:** 3, Edge

## Context

In the previous setup, nginx in a container is the only TLS entry point, with certbot in another container. The router forwards 80, 443 and a range of ports for VMs to the server and is the only firewall. On 443 an `ssl_preread` stream block routes by SNI: the Incus UI and API go through untouched (client-certificate mTLS), and everything else goes to an internal HTTP block with the PROXY protocol, so the services see the real client IP. One ECDSA certificate with about 20 names (ten virtual hosts, most of them on two domains: the real domain and a dynamic-DNS name) is requested with `certonly --webroot --force-renewal`, so every run issues a new certificate. A cron job restarts certbot on five days a month, and nginx only rereads the certificate when someone reloads it. DNS is at an external provider and is changed by hand.

What went wrong there (from its own incident log), and what it means for this phase:

| Problem | Lesson |
|---|---|
| TLS 1.2 dead on every virtual host: the cipher lists held only RSA suites against an ECDSA certificate; on the media servers TLS 1.1 was still enabled | the TLS settings were copied into eleven server blocks and drifted: they must exist once |
| The client IP was always `127.0.0.1` in the logs, after the internal SNI hop | the real IP must reach the services without a hand-written patch script |
| A button injected into Jellyfin's login page with `sub_filter`, by a patch script run against `nginx.conf` | patches to a generated file are exactly the glue [P1](../principles.md) refuses |
| nginx starts only if every upstream resolves, so one missing container takes the whole site down; recreating a container changes its IP and gives a 502 until a manual reload | one backend failing must not stop the others, and a restart of a backend must not need a manual step |
| Forced renewal on every run risks Let's Encrypt's duplicate-certificate limit; a certificate renewed on disk is not the one nginx serves until it is reloaded | renewal must reload by itself, and must not be forced |
| The same `EMAIL` variable reused by two scripts, once overwritten by the SMTP user | the account and the contact belong to the configuration, not to a shared variable |
| The configuration is a 902-line file, plus three patch scripts | configuration as data, generated from a short description |

## Requirements

- Must:
  - HTTPS for every service name, TLS 1.2 and 1.3 only, an ECDSA certificate, HTTP redirected to HTTPS, HSTS, the same hardening on every name, declared once;
  - certificates obtained and renewed by the system itself (no forced renewal, a reload without dropping connections, a failure is noticed);
  - the proxy keeps working for what the services use: WebSockets (Immich, Jellyfin, Nextcloud, Vaultwarden), very large uploads (up to 50 GB), long streams (timeouts of hours) and range requests;
  - the real client IP reaches every service;
  - one failed backend does not stop the others, and a backend that comes back is used again without a manual reload;
  - everything in the flake: no patch script, no hand-edited file; secrets through [ADR 0003](0003-secrets.md).
- Should:
  - only what must be public is public: the services are used from phones and from outside the house, but the Incus API on `0.0.0.0` and the forwarded VM ports are exposures to question here and in phase 6;
  - HTTP/2, and HTTP/3 if it comes free;
  - an SNI passthrough for the Incus UI and API (mTLS must keep working) if Incus stays;
  - an HTML injection for Jellyfin's SSO button, done by a documented feature of the proxy, not a patch script;
  - basic authentication for a personal site, from a secret file.
- Should not: a WAF, a CDN, a service mesh, Kubernetes ingress. The DNS records and the router's port forwarding are outside the server and stay manual by nature: they are documented, not automated, unless the DNS provider's API makes the certificate part easy.

## Options considered

| Option | What it is |
|---|---|
| A. nginx through the NixOS module, with the NixOS ACME module | `services.nginx` and `security.acme` (lego), virtual hosts declared in Nix, certificates by HTTP-01 or DNS-01, reload through the module |
| B. Caddy through `services.caddy` | automatic HTTPS built in, a short configuration, HTTP/3; the SNI passthrough and the HTML injection need third-party plugins (a custom build) |
| C. Traefik through `services.traefik` | routers and middlewares as data, built-in ACME, TCP routing by SNI; HTML injection only through a third-party plugin |
| D. The previous setup as it is | the baseline, measured in lines and in incidents, not rebuilt |

Certificates are a second axis: one certificate for all names or one per name; HTTP-01 (port 80 reachable) or DNS-01 (a wildcard, a DNS provider API token that would be a secret); and whether a dynamic-DNS name can use DNS-01 at all (usually not).

Criteria, in this order, fixed before testing: the P1 gate (a maintained NixOS module or a documented feature for everything in Must; a requirement that needs a plugin or a custom build counts against the option); the certificate lifecycle; behaviour under the services' load; failure isolation; security posture; size and clarity of the configuration; fit with what comes later.

## Results

`lab/experiments/edge-bakeoff.sh`, in the NixOS lab VM. Fixtures: Pebble (a test ACME CA, with a DNS that answers 127.0.0.1 for every name, so the challenges are real HTTP-01 ones), six lab backends standing for what the services need (request headers, a counted upload, a WebSocket echo, an answer after 75 s, an HTML page to modify, a missing backend) and a seventh that demands a client certificate, as Incus does. Each name exists on two domains: 12 names for the web checks, plus one for the passthrough.

| Check | A. nginx + NixOS ACME | B. Caddy | C. Traefik |
|---|---|---|---|
| Certificates for all 12 names after the machine starts | 14 s, nginx already serving (it starts with placeholder certificates) | under 25 s | under 25 s |
| Protocols offered | TLS 1.2 and 1.3 only | the same | the same |
| HSTS and two more headers, declared once | yes (`appendHttpConfig`) | yes (a snippet) | yes (a middleware) |
| Real client IP at the backend | yes, through the SNI stream and PROXY protocol: two stream servers and two `real_ip` lines | yes | yes, with no relay |
| WebSocket, 3 GB upload, a 75 s answer | yes, after `clientMaxBodySize` and `proxyTimeout` are set (the module defaults are 10 MB and 60 s) | yes, with no setting | yes, after `readTimeout = 0` |
| A missing backend | 502, the others unaffected | 502 | 502 |
| A literal upstream name that does not resolve | nginx refuses to start: `host not found in upstream` | starts, 502 at the request | starts, 502 at the request |
| HTML injection (the SSO button) | yes, `sub_filter`, a documented feature | no: needs a third-party plugin | no: only through a plugin |
| TLS passthrough by SNI, mTLS to the backend | yes: a stream block, plus a relay that strips the PROXY header | no: needs the layer4 plugin | yes, native, no relay |
| Renewal | a forced re-issue: new serial, nginx reloaded by the module, a 75 s request open during it finished normally | a 20-minute certificate renewed in the process, with no reload; an idle WebSocket across the renewal still answered | not demonstrated: it checks once a day, so a 20-minute certificate never renewed |
| Lines of our own configuration, without comments | 57 (all features above) | 33 (without injection and passthrough) | 48 (without injection) |
| The previous setup, for comparison | 535 lines of `nginx.conf` plus 322 lines of patch scripts | | |

What a plugin costs in Caddy: `caddy.withPlugins` builds a custom Caddy; it compiled in about 100 s, but it demands exact plugin versions and a fixed-output hash that is learned by a failed build and recomputed by hand whenever Caddy or a plugin changes. That is the opposite of "change a version and run the same checks".

For certificates by DNS challenge (a wildcard, nothing exposed on port 80), the NixOS ACME module supports many DNS providers natively, with the credentials as a file (so a sops secret); Traefik does as well; Caddy needs a plugin per provider.

What the lab showed about running them:

- The NixOS ACME module starts nginx with placeholder certificates, so the proxy comes up before any order succeeds, and replaces them when they arrive.
- After one order failed (my own configuration error), the other orders reported `Dependency failed` instead of running: one failing name delays the others until it is fixed.
- The module exposes native options for what the previous setup patched by script (`clientMaxBodySize`, `proxyTimeout`, `sslProtocols`, the recommended proxy and TLS settings); a directive set twice (once by an option and once by hand) fails the whole configuration.
- IPv6 matters: the test CA validated over `::1`, so the HTTP-01 server must listen on IPv6 as well.
- Lab errors of mine, kept because they are the kind a real configuration makes: merging two definitions of a virtual host with `//` replaced the whole first one (use `recursiveUpdate`).

Not tested in this first round: a real DNS provider and DNS-01 (tried afterwards, below); Let's Encrypt itself; OCSP stapling; HTTP/3 on nginx; Traefik's renewal; the plugins of Caddy; fail2ban against the proxy's logs and rate limiting; logging and metrics (phase 5); the real Incus.

## Decision

nginx through the NixOS module, with the NixOS ACME module. Why, by the criteria in order:

1. P1 gate: only A meets every Must and both Should items (the HTML injection and the SNI passthrough) with documented features and no custom build. C lacks the injection; B lacks both without a custom build with a hash to refresh.
2. Certificate lifecycle: all three issue within seconds; A reloads gracefully on renewal and was shown not to drop a request; B renews in the process; C's renewal is not demonstrated with short-lived certificates.
3. Load, isolation, security: all three pass. The defaults of A and C must be raised (two options in A, one in C), and A's one weakness, refusing to start over an unresolvable upstream name, does not apply while the backends are addressed by `127.0.0.1` and a port, which is how the containers and native services are reached.
4. Size: C and B are shorter, but they omit features I use; A at 57 lines does all of it, against 535 lines and three patch scripts before.
5. Fit with what comes later: A keeps the previous design (passthrough to Incus, injection for the SSO button) in code, which phases 4 and 6 need.

Two caveats. Traefik is the cleaner answer if the SSO button is dropped and Incus passthrough is wanted without a relay. And DNS-01 works natively in A and C but not in B.

### Names and exposure

- One domain is served. Its names are CNAMEs to the dynamic-DNS name, which stops being a name the services answer on, so the certificates cover only the domain (about ten names instead of twenty) and the ACME challenge reaches the server through the CNAME.
- Public (reachable from anywhere): Immich, Nextcloud, Vaultwarden, WebDAV and Jellyfin.
- Only through the VPN ([ADR 0009](0009-remote-access-vpn.md)): the Incus UI and API, Syncthing's GUI, the router's page, a personal site, SSH, and the services of virtual machines ([ADR 0010](0010-vm-service-exposure.md)).
- Syncthing: the sync is public and the GUI is VPN-only. Its sync port (22000, TCP and UDP) stays forwarded by the router; the GUI listens on the VPN address only. The sync is authenticated by device certificates, and local discovery on 21027 is a LAN broadcast that the firewall opens on the LAN interface only.
- Plex is dropped; Jellyfin stays.

With the Incus API on the VPN address only, the passthrough of its mutual-TLS login from the Internet disappears, and with it the stream front end, the relay and the PROXY protocol that nginx needed for it (about eight of its 57 lines). That also removes Traefik's one advantage and leaves Caddy lacking only the HTML injection and, for DNS challenges, a plugin. nginx stays because the HTML injection for the SSO button is a documented feature of nginx only.

Unknown names are refused at the TLS handshake with a default virtual host (`rejectSSL`), which also keeps the server from answering for a name it does not serve. When one certificate order failed at boot, the others were skipped and the names stayed on placeholder certificates until the orders were started again (the renewal timers run every 12 hours). So a failed order needs an alert, and the first deployment needs a check that every name has its real certificate.

## The DNS challenge

The VPN-only names and any wildcard need the DNS challenge (a name that is not reachable from the Internet cannot answer an HTTP challenge). The DNS provider has an API that needs a business account and takes second-level domains, and `lego`, the client the NixOS ACME module uses, has no provider for it.

| Route | What it takes | P1 |
|---|---|---|
| 1. Delegate the challenge name by CNAME to a provider `lego` supports (deSEC, free; or acme-dns, run privately or public) | a few one-time CNAME records at the DNS provider (`_acme-challenge` and one for each name that needs it); the provider's token as a sops secret; `lego` follows the CNAME | clean: a documented ACME mechanism, no script; the token can obtain certificates for the delegated names |
| 2. Move the DNS hosting to a provider `lego` supports | one change at the registrar; every other record (mail: MX, SPF, DKIM) must be recreated | clean, but the larger change |
| 3. Use the provider's API through `lego`'s `exec` or `httpreq` provider with a small script | a script and a business API account | glue: an exception to enter in [the register](../exceptions.md) |
| 4. No DNS challenge: HTTP-01 for the public names and a private CA for the VPN-only ones | a small CA service and its root trusted on every device | clean for the public names; one more service, and a root to install on each device |

I tried route 1. Two known problems exist on this path (the certbot plugin for deSEC did not follow CNAMEs until a later release, and `lego` had a case where its deSEC provider split a domain into the wrong zone, [issue 2353](https://github.com/go-acme/lego/issues/2353)), so it was tested with a real provider against Let's Encrypt's staging service, for a name that does not exist publicly. The provider was the public acme-dns, registered anonymously.

It works end to end through the NixOS ACME module (`lab/experiments/acme-delegation-test.sh`):

- One CNAME at the DNS provider, `_acme-challenge.test` pointing at the registration's name. `lego` found it ("Found CNAME entry") and followed it, wrote the challenge there, waited for the propagation check, and Let's Encrypt validated. The certificate came about 13 seconds after the order started, 10 of them the propagation wait.
- The same single CNAME also served a wildcard: one issuance for `test.<domain>` and `*.test.<domain>`, because the label is shared.
- The credentials file was read-only (mode 400, owned by the unit's user) and the order succeeded, so a sops-nix secret fits, provided it is owned by the `acme` user: a root-owned file made `lego` fail with a message that says "failed to write storage file" but means "cannot read it".
- The module needs only four lines for a name (`dnsProvider = "acme-dns"`, an `environmentFile` with `ACME_DNS_API_BASE` and `ACME_DNS_STORAGE_PATH`, `dnsPropagationCheck`, and `extraDomainNames` for the wildcard).
- A real CA refuses a contact address without a public suffix (`lab@example.test`): the account address belongs under the real domain.

What the DNS provider taught: its four nameservers did not all serve the new record at once. Two had it within minutes and the other two took about 25 minutes, so a record change has to be left to settle before a test or an issuance. And a wildcard CNAME in the zone is overridden by a specific record.

Not tested: deSEC; acme-dns hosted at home (it needs a delegation of a sub-zone to the server and port 53 exposed to the Internet, one more public service); the renewal cycle; the production CA's limits.

The trust question: whoever controls the challenge zone can answer the challenge for the delegated names, so a third-party instance (the public acme-dns) means trusting it, and the credentials let the holder write there. Two hardenings, neither tested here: the account's `allowfrom` list, and a CAA record that binds issuance to my own ACME account (`accounturi`), which stops a certificate being issued by anyone else even if the challenge zone is controlled. A CAA record on the apex (`issue` and `issuewild` for `letsencrypt.org; validationmethods=dns-01`) is returned by a public resolver, and the blackbox probe of [ADR 0012](0012-observability.md) reads it and a rule fires if it disappears. Whether the CAA blocks a foreign issuer was not tested, since it needs a second ACME account. The binding to my account waits for the first real issuance.

Route 1 keeps the DNS provider as it is, adds no script and no service, and needs two CNAME records (one for the domain's names, one for the VM names). I accept the public acme-dns as a third party, with the hardenings above. Caddy would need a plugin per provider; the NixOS module and Traefik would not.

## Decision, summarized

- nginx through the NixOS module, with the NixOS ACME module (lego): every virtual host declared in Nix, no stream front end and no PROXY protocol (the Incus API is VPN-only, [ADR 0010](0010-vm-service-exposure.md)), the HTML injection for the SSO button by `sub_filter`, unknown names refused at the handshake.
- One domain, whose names are CNAMEs to the dynamic-DNS name; certificates for that domain only.
- The split above: public Immich, Nextcloud, Vaultwarden, WebDAV, Jellyfin and Syncthing's sync port; VPN-only the rest.
- Certificates by the DNS challenge with the challenge name delegated by CNAME to the public acme-dns: two wildcard certificates, `<domain>` with `*.<domain>`, and `*.compute.<domain>` (the instances' names), from two registrations and two CNAME records at the DNS provider (`_acme-challenge` and `_acme-challenge.compute`). The registrations' credentials are one sops secret, `acme-dns-credentials` (lego's JSON, one entry per certificate name), owned by the `acme` user; the host builds the environment file itself (`tidepool.acmeDns.apiBase`, the public instance by default). Checked by running `lego` against a stand-in API: it reads the file by the certificate's name, does not register again and authenticates with the stored user and key.
- Hardening, to do when the system issues for the first time: the CAA record with `accounturi`. `allowfrom` is not used: it restricts the address that may update the challenge record, but a home address is dynamic, and as far as the API shows it cannot be changed after the registration.
- The first deployment must check that every name has its real certificate, and a failed order needs an alert (phase 5).

## The names

The names say what the service is for, not which program serves it: `media.` (Jellyfin), `backup.` (WebDAV), `push.` (ntfy), `cloud.` (Nextcloud, with the calendar and the contacts), `photos.`, `vault.` and `sync.`. The tools that had no name get one, VPN only: `metrics.` (Prometheus), `alerts.` (Alertmanager) and `compute.` (Incus, on its own port, because of its client certificates). The list, and what the DNS provider needs for it, is in [the names page](../names.md).

The names of the instances ([ADR 0010](0010-vm-service-exposure.md)) add a second wildcard, `*.compute.<domain>`, which `*.<domain>` does not cover (a wildcard is one label deep). It is ordered as its own certificate by the same acme-dns, and needs one more CNAME at the DNS provider, `_acme-challenge.compute`, with its own registration. A client that used an old name (the Jellyfin and Seedvault apps, the ntfy app) is pointed at the new one at the cutover.
