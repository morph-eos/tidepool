# 0008. The edge: how traffic reaches the services, and with which certificates

- **Status:** proposed (requirements and criteria written before any test; the lab results and the decision follow)
- **Date:** 2026-10-01
- **Phase:** 3, Edge

## Context

In v0, **nginx in a container is the only TLS entry point**, with certbot in another container. The router forwards 80, 443 and the range 3000-3099 to the server and is the only firewall (UFW is off).
On 443 an `ssl_preread` stream block routes by SNI: the Incus UI and API go through untouched (client-certificate mTLS), everything else goes to an internal HTTP block on 8442 with the PROXY protocol, so the services see the real client IP.
**One ECDSA certificate with 20 names** (ten virtual hosts, most of them on two domains: the owner's domain and a dynamic-DNS name; the router's own page, `modem`, and a personal site are among them) is requested with `certonly --webroot --force-renewal`, **so every run issues a new certificate**; a cron job restarts certbot on five days a month, and **nginx only rereads the certificate when someone reloads it**.
DNS is at an external provider and **is changed by hand**.

What went wrong in v0 (from its own incident log), and what it means for this phase:

| v0 problem | Lesson |
|---|---|
| TLS 1.2 dead on every vhost: the cipher lists held only RSA suites against an ECDSA certificate; on **Jellyfin and Plex `TLSv1.1` is still enabled** | the TLS settings were copied into eleven server blocks and drifted: they must exist **once** |
| The client IP was always `127.0.0.1` in the logs, after the internal SNI hop | the real IP must reach the services without a hand-written patch script |
| A button injected into Jellyfin's login page with `sub_filter`, by a patch script run against `nginx.conf` | patches to a generated file are exactly the glue [P1](../principles.md) refuses |
| `nginx` starts only if every upstream resolves, so **one missing container takes the whole site down**; recreating a container changes its IP and gives a 502 until a manual reload | one backend failing must not stop the others, and a restart of a backend must not need a manual step |
| Forced renewal on every run risks Let's Encrypt's duplicate-certificate limit; a certificate renewed on disk is **not** the one nginx serves until it is reloaded | renewal must reload by itself, and must not be forced |
| `EMAIL` reused by two scripts, once overwritten by the SMTP user | the account and the contact belong to the configuration, not to a shared variable |
| The configuration is a 902-line file, plus three patch scripts | configuration as data, generated from a short description |

## Requirements

- **Must:**
  - HTTPS for every service name (ten virtual hosts, most on two domains), **TLS 1.2 and 1.3 only**, an ECDSA certificate, HTTP redirected to HTTPS, HSTS, the same hardening on every name, declared once;
  - **certificates obtained and renewed by the system itself** (no forced renewal, **a reload without dropping connections**, a failure is noticed);
  - the proxy keeps working for what the services use: **WebSockets** (Immich, Jellyfin, Nextcloud, Vaultwarden), **very large uploads** (v0 allows 1 GB by default, 10 GB for Nextcloud, 20 GB for WebDAV and 50 GB on Jellyfin and Plex locations), **long streams** (timeouts of hours) and **range requests**;
  - the **real client IP** reaches every service;
  - **one failed backend does not stop the others**, and a backend that comes back is used again without a manual reload;
  - everything in the flake: no patch script, no hand-edited file; secrets (an ACME account key, a DNS token if one is needed) through [ADR 0003](0003-secrets.md).
- **Should:**
  - **only what must be public is public**: the owner's services are used from phones and from outside the house, but the Incus API on `0.0.0.0` and the VM ports 3000-3099 forwarded by the router are exposures to question here and in phase 6;
  - HTTP/2, and HTTP/3 if it comes free;
  - an **SNI passthrough** for the Incus UI and API (mTLS must keep working) **if Incus stays** (phase 6 decides);
  - an HTML injection for Jellyfin's SSO button, done by a documented feature of the proxy, not a patch script (the SSO design itself is phase 4);
  - the certificate shared with Incus, if it stays, with the reload done by the system;
  - basic authentication for the personal site, from a secret file.
- **Won't:** a WAF, a CDN, a service mesh, Kubernetes ingress. The DNS records and the router's port forwarding are **outside the server** and stay manual by nature: they are documented, not automated, unless the DNS provider's API makes the certificate part easy.

## Options considered

| Option | What it is |
|---|---|
| **A. nginx through the NixOS module, with the NixOS ACME module** | `services.nginx` and `security.acme` (lego), virtual hosts declared in Nix, certificates by HTTP-01 or DNS-01, reload through the module |
| **B. Caddy through `services.caddy`** | automatic HTTPS built in, a short configuration, HTTP/3; the SNI passthrough and the HTML injection need **third-party plugins** (a custom build) |
| **C. Traefik through `services.traefik`** | routers and middlewares as data, built-in ACME, TCP routing by SNI; HTML injection only through a third-party plugin |
| **D. v0 as it is: nginx and certbot in containers** | the baseline: what v0 does, measured in lines and in incidents, not rebuilt |

Certificates are a second axis, not a separate product: **one certificate for all names or one per name**; **HTTP-01** (port 80 reachable) or **DNS-01** (a wildcard, a DNS provider API token that would be a secret); and whether the **dynamic-DNS name** can use DNS-01 at all (usually not).

## Criteria, in this order (fixed before testing)

1. **P1 gate:** a maintained NixOS module, or a documented feature, for everything in *Must*; no patch script and no generated file edited by hand. A requirement that needs a third-party plugin or a custom build is **a cost counted against the option**.
2. **Certificate lifecycle** (measured): time from an empty machine to a served certificate; a renewal that happens by itself, and **reloads without dropping a connection**; what happens when the CA or the DNS fails.
3. **Behaviour under the services' load** (measured): WebSocket, a multi-gigabyte upload, a long idle stream, range requests, the real client IP.
4. **Failure isolation** (measured): a missing or restarted backend, and the others.
5. **Security posture** (measured): the protocols and ciphers actually offered, headers on every name, declared once.
6. **Size and clarity of the configuration:** lines of our own for ten virtual hosts on two domains, against v0's 902 lines and three patch scripts.
7. **Fit with what comes later:** Incus SNI passthrough, Jellyfin's SSO button, certificate sharing, observability (phase 5).

## Questions for the owner (they change the design, not only the tool)

1. **Which services must be reachable from the Internet without a VPN?** The phone apps (Immich, Nextcloud, Vaultwarden, WebDAV) and Jellyfin for the family are the likely ones. Everything else (the Incus UI, Syncthing's GUI, the personal site) could be reachable only from the house or through a VPN.
2. **Why two names for every service** (the owner's domain and the dynamic-DNS name)? Is the second one still needed, for instance because the home address changes, or can the first be kept up to date by the DNS provider's API?
3. **Which provider hosts the DNS of the main domain, and does it have an API?** That decides whether a **wildcard certificate by DNS-01** is possible (one certificate, no port 80 needed, nothing exposed for the challenge) or only HTTP-01.
4. **Is a VPN (WireGuard, or a service built on it) acceptable** for the administration surfaces and for the devices of the family, to reduce what the router forwards?
