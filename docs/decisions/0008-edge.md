# 0008. The edge: how traffic reaches the services, and with which certificates

- **Status:** proposed (lab results in; recommendation: nginx through the NixOS module with the NixOS ACME module; one domain with CNAMEs; the split is agreed; the DNS-challenge route, with the DNS at the provider, waits for a test)
- **Date:** 2026-10-01
- **Phase:** 3, Edge

## Context

In v0, **nginx in a container is the only TLS entry point**, with certbot in another container. The router forwards 80, 443 and the range 3000-3099 to the server and is the only firewall (UFW is off).
On 443 an `ssl_preread` stream block routes by SNI: the Incus UI and API go through untouched (client-certificate mTLS), everything else goes to an internal HTTP block on 8442 with the PROXY protocol, so the services see the real client IP.
**One ECDSA certificate with 20 names** (ten virtual hosts, most of them on two domains: the owner's domain and a dynamic-DNS name; the router's own page, `modem`, and a personal site are among them) is requested with `certonly --webroot --force-renewal`, **so every run issues a new certificate**; a cron job restarts certbot on five days a month, and **nginx only rereads the certificate when someone reloads it**.
DNS is at an external provider and **is changed by hand**.

What went wrong in v0 (from its own incident log), and what it means for this phase:

| v0 problem | Lesson |
|---|---|
| TLS 1.2 dead on every vhost: the cipher lists held only RSA suites against an ECDSA certificate; on **Jellyfin and Plex `TLSv1.1` is still enabled** | the TLS settings were copied into eleven server blocks and drifted: they must exist **once** |
| The client IP was always `127.0.0.1` in the logs, after the internal SNI hop | the real IP must reach the services without a hand-written patch script |
| A button injected into Jellyfin's login page with `sub_filter`, by a patch script run against `nginx.conf` | patches to a generated file are exactly the glue [P1](../principles.md) refuses |
| `nginx` starts only if every upstream resolves, so **one missing container takes the whole site down**; recreating a container changes its IP and gives a 502 until a manual reload | one backend failing must not stop the others, and a restart of a backend must not need a manual step |
| Forced renewal on every run risks Let's Encrypt's duplicate-certificate limit; a certificate renewed on disk is **not** the one nginx serves until it is reloaded | renewal must reload by itself, and must not be forced |
| `EMAIL` reused by two scripts, once overwritten by the SMTP user | the account and the contact belong to the configuration, not to a shared variable |
| The configuration is a 902-line file, plus three patch scripts | configuration as data, generated from a short description |

## Requirements

- **Must:**
  - HTTPS for every service name (ten virtual hosts, most on two domains), **TLS 1.2 and 1.3 only**, an ECDSA certificate, HTTP redirected to HTTPS, HSTS, the same hardening on every name, declared once;
  - **certificates obtained and renewed by the system itself** (no forced renewal, **a reload without dropping connections**, a failure is noticed);
  - the proxy keeps working for what the services use: **WebSockets** (Immich, Jellyfin, Nextcloud, Vaultwarden), **very large uploads** (v0 allows 1 GB by default, 10 GB for Nextcloud, 20 GB for WebDAV and 50 GB on Jellyfin and Plex locations), **long streams** (timeouts of hours) and **range requests**;
  - the **real client IP** reaches every service;
  - **one failed backend does not stop the others**, and a backend that comes back is used again without a manual reload;
  - everything in the flake: no patch script, no hand-edited file; secrets (an ACME account key, a DNS token if one is needed) through [ADR 0003](0003-secrets.md).
- **Should:**
  - **only what must be public is public**: the owner's services are used from phones and from outside the house, but the Incus API on `0.0.0.0` and the VM ports 3000-3099 forwarded by the router are exposures to question here and in phase 6;
  - HTTP/2, and HTTP/3 if it comes free;
  - an **SNI passthrough** for the Incus UI and API (mTLS must keep working) **if Incus stays** (phase 6 decides);
  - an HTML injection for Jellyfin's SSO button, done by a documented feature of the proxy, not a patch script (the SSO design itself is phase 4);
  - the certificate shared with Incus, if it stays, with the reload done by the system;
  - basic authentication for the personal site, from a secret file.
- **Won't:** a WAF, a CDN, a service mesh, Kubernetes ingress. The DNS records and the router's port forwarding are **outside the server** and stay manual by nature: they are documented, not automated, unless the DNS provider's API makes the certificate part easy.

## Options considered

| Option | What it is |
|---|---|
| **A. nginx through the NixOS module, with the NixOS ACME module** | `services.nginx` and `security.acme` (lego), virtual hosts declared in Nix, certificates by HTTP-01 or DNS-01, reload through the module |
| **B. Caddy through `services.caddy`** | automatic HTTPS built in, a short configuration, HTTP/3; the SNI passthrough and the HTML injection need **third-party plugins** (a custom build) |
| **C. Traefik through `services.traefik`** | routers and middlewares as data, built-in ACME, TCP routing by SNI; HTML injection only through a third-party plugin |
| **D. v0 as it is: nginx and certbot in containers** | the baseline: what v0 does, measured in lines and in incidents, not rebuilt |

Certificates are a second axis, not a separate product: **one certificate for all names or one per name**; **HTTP-01** (port 80 reachable) or **DNS-01** (a wildcard, a DNS provider API token that would be a secret); and whether the **dynamic-DNS name** can use DNS-01 at all (usually not).

## Criteria, in this order (fixed before testing)

1. **P1 gate:** a maintained NixOS module, or a documented feature, for everything in *Must*; no patch script and no generated file edited by hand. A requirement that needs a third-party plugin or a custom build is **a cost counted against the option**.
2. **Certificate lifecycle** (measured): time from an empty machine to a served certificate; a renewal that happens by itself, and **reloads without dropping a connection**; what happens when the CA or the DNS fails.
3. **Behaviour under the services' load** (measured): WebSocket, a multi-gigabyte upload, a long idle stream, range requests, the real client IP.
4. **Failure isolation** (measured): a missing or restarted backend, and the others.
5. **Security posture** (measured): the protocols and ciphers actually offered, headers on every name, declared once.
6. **Size and clarity of the configuration:** lines of our own for ten virtual hosts on two domains, against v0's 902 lines and three patch scripts.
7. **Fit with what comes later:** Incus SNI passthrough, Jellyfin's SSO button, certificate sharing, observability (phase 5).

## Results

`lab/edge-bakeoff.sh`, in the NixOS lab VM (`exp/edge-nginx`, `exp/edge-caddy`, `exp/edge-traefik`). Fixtures: **Pebble** (a test ACME CA, with a DNS that answers 127.0.0.1 for every name, so the challenges are real HTTP-01 ones on port 80), six lab backends standing for what v0's services need
(request headers, a counted upload, a WebSocket echo, an answer after 75 s, an HTML page to modify, a missing backend) and a seventh that demands a **client certificate**, as Incus does.
Each name exists on two domains, as in v0: 12 names for the web checks, plus one for the passthrough. Candidate D (v0) is not rebuilt: it is measured by its files and its incident log.

| Check | A. nginx + NixOS ACME | B. Caddy | C. Traefik |
|---|---|---|---|
| Certificates for all 12 names after the machine starts | **14 s**, nginx already serving (it starts with placeholder certificates) | under 25 s | under 25 s |
| Protocols offered (testssl) | TLS 1.2 and 1.3 only | the same | the same |
| HTTP to HTTPS | 301 | 308 | 301 |
| HSTS and two more headers, declared once | yes (`appendHttpConfig`) | yes (a snippet) | yes (a middleware) |
| HTTP version | 2 | 2 (3 is on by default) | 2 |
| **Real client IP** at the backend (client at 127.0.0.2) | **yes**, through the SNI stream and PROXY protocol: two stream servers and two `real_ip` lines | yes | yes, with **no relay** |
| WebSocket, 3 GB upload, a 75 s answer | yes, **after** `clientMaxBodySize` and `proxyTimeout` are set (the module defaults are 10 MB and 60 s) | yes, with no setting | yes, **after** `readTimeout = 0` (the default of 60 s is documented, not re-measured) |
| A missing backend | 502, the others unaffected | 502 | 502 |
| **A literal upstream name that does not resolve** | **nginx refuses to start**: `host not found in upstream` (v0's problem) | starts, 502 at the request | starts, 502 at the request |
| **HTML injection** (v0's SSO button) | **yes**, `sub_filter`, a documented feature | **no**: needs a third-party plugin | **no**: only through a plugin |
| **TLS passthrough by SNI, mTLS to the backend** | **yes**: a stream block, plus a relay that strips the PROXY header (the same shape as v0, declared) | **no**: needs the layer4 plugin | **yes, native**, on the same port as the HTTP routers, no relay |
| **Renewal** | forced a re-issue: new serial, **nginx reloaded by the module**, a 75 s request open during it **finished normally** | a 20-minute certificate renewed **in the process, with no reload**, after about 10 minutes; a WebSocket idle for 15 minutes across the renewal **still answered** | **not demonstrated**: it checks once a day, so a 20-minute certificate never renewed; with normal 90-day certificates a daily check is ample |
| Lines of our own configuration, without comments | 57 (all features above) | 33 (**without** injection and passthrough) | 48 (**without** injection) |
| v0 for comparison | 535 lines of `nginx.conf` plus 322 lines of patch scripts | | |

**What a plugin costs in Caddy** (tried): `caddy.withPlugins` builds a custom Caddy; it compiled in about 100 s, but it demands **exact plugin versions** (a branch name was refused) and a **fixed-output hash** that is learned by a failed build and **recomputed by hand whenever Caddy or a plugin changes**. That is the opposite of "change a version and run the same checks". The functional behaviour of those plugins was **not tested**.

**Certificates by DNS challenge** (a wildcard, nothing exposed on port 80): the NixOS ACME module supports many DNS providers natively, with the credentials as a file (so a sops secret); Traefik does as well, through environment variables; **Caddy needs a plugin per provider**. Whether this matters depends on the owner's DNS provider (open question 3).

What the lab showed about running them:
- **The NixOS ACME module starts nginx with placeholder certificates**, so the proxy comes up before any order succeeds, and replaces them when they arrive.
- **In the first run, after one order failed (my own configuration error), the other orders reported `Dependency failed`** instead of running: one failing name delays the others until it is fixed.
- **The module exposes native options for what v0 patched by script** (`clientMaxBodySize`, `proxyTimeout`, `sslProtocols`, the recommended proxy and TLS settings); **a directive set twice** (once by an option and once by hand) **fails the whole configuration**.
- **IPv6 matters**: the test CA validated over `::1`, so the HTTP-01 server must listen on IPv6 as well.
- **Lab errors of mine, kept here because they are the kind a real configuration makes**: merging two definitions of a virtual host with `//` replaced the whole first one (use `recursiveUpdate`); an ACME client's account lives on disk and the test CA forgets it at every restart (a lab artefact: a real CA does not).

**Not tested:** a real DNS provider and DNS-01; Let's Encrypt itself (staging, limits); OCSP stapling; HTTP/3 on nginx; Traefik's renewal; the plugins of Caddy; fail2ban against the proxy's logs and rate limiting; logging and metrics (phase 5); the real Incus.

## Decision

_Recommended, pending the owner's answers below: **A, nginx through the NixOS module with the NixOS ACME module.**_

Why, by the criteria in order:
1. **P1 gate:** only A meets every *Must* **and** both *Should* items (the HTML injection and the SNI passthrough) with documented features and no custom build. C lacks the injection; B lacks both without a custom build with a hash to refresh.
2. **Certificate lifecycle:** all three issue within seconds; A reloads gracefully on renewal and was shown not to drop a request; B renews in the process; C's renewal is not demonstrated with short-lived certificates.
3. to 5. **Load, isolation, security:** all three pass; the defaults of A and C must be raised for v0's workloads (it is two options in A, one in C), and A's one weakness, **refusing to start over an unresolvable upstream name**, does not apply while the backends are addressed by `127.0.0.1` and a port, which is how the planned containers and native services are reached.
6. **Size:** C and B are shorter, but they omit features the owner uses; A at 57 lines does all of it, against 535 lines and three patch scripts in v0.
7. **Fit with what comes later:** A keeps v0's design (passthrough to Incus, injection for the SSO button) in code, which phases 4 and 6 need.
Two caveats: Traefik is the cleaner answer if the SSO button is dropped in favour of another login design (a phase 4 question) and Incus passthrough is wanted without a relay; and **DNS-01** works natively in A and C but not in B.

**The certificate strategy waits for the owner's answers** (HTTP-01 per name, by default; or a DNS-01 wildcard if the DNS provider has an API) and so does **what is exposed** (questions 1 and 4).

## The owner's answers (2026-10-01)

- **Names:** in v1 **only the owner's domain is served**; its names are **CNAMEs to the dynamic-DNS name** (which v0 added later, once the domain already existed). The DDNS name stops being a name the services answer on, so **the certificates cover only the owner's domain** (about ten names instead of twenty) and the ACME challenge reaches the server through the CNAME.
- **The split, accepted as proposed:**
  - **Public** (reachable from anywhere): **Immich, Nextcloud, Vaultwarden, WebDAV and Jellyfin** (for the family).
  - **Only through the VPN** ([ADR 0009](0009-remote-access-vpn.md)): **the Incus UI and API, Syncthing's GUI, the router's page, the personal site, SSH, and the services of virtual machines** ([ADR 0010](0010-vm-service-exposure.md)).
  - Not part of the split and still to settle: **Syncthing's own sync port** (22000, not HTTP) and Plex (off in v0).
- **The DNS is at the domain's registrar**. See below.

**Consequence of the VPN for the proxy.** With the Incus API **on the VPN address only** ([ADR 0010](0010-vm-service-exposure.md)), the **passthrough of its mutual-TLS login from the Internet disappears**, and with it the stream front end, the relay and the PROXY protocol that the nginx candidate needed for it (about eight lines of its 57). That also **removes Traefik's one advantage** (a native passthrough) and leaves Caddy lacking only the HTML injection and, for DNS challenges, a plugin. nginx stays the recommendation because **the HTML injection for the SSO button is a documented feature of nginx only**.

What the VPN test added to this ADR's findings (details in [ADR 0009](0009-remote-access-vpn.md)): **unknown names are refused at the TLS handshake** with a default virtual host (`rejectSSL`), which also keeps the server from answering for a name it does not serve; and, **when one certificate order failed at boot, the other orders were skipped with `Dependency failed`** and the names stayed on placeholder certificates until the orders were started again (the renewal timers run every 12 hours), so a failure needs an alert and the first deployment needs a check that every name has its real certificate.

### The DNS challenge, with the DNS at the provider

The VPN-only names and any wildcard need the **DNS challenge** (a name that is not reachable from the Internet cannot answer an HTTP challenge). What was found (searches and a check in the lab, not a test with the DNS provider):
- **The provider has a DNS API**: the key is obtained with a business account at the provider, a token is issued per day, and the API takes **second-level domains**. A community plugin exists for `acme.sh` ([the pull request](https://github.com/acmesh-official/acme.sh/pull/2848)). Whether a plain domain customer can use it, and at what price, **was not verified**.
- **`lego`, the client the NixOS ACME module uses, has no provider for the owner's DNS host**: the lab's `lego dnshelp` lists acme-dns, Cloudflare, deSEC, Gandi, Hetzner, Namecheap, OVH, Porkbun and others, **not the owner's DNS host**.

| Route | What it takes | P1 |
|---|---|---|
| **1. Delegate the challenge name by CNAME** to a provider `lego` supports (**deSEC**, free; or **acme-dns**, run by the owner or public; or another with an API): a few **one-time CNAME records at the DNS provider** (`_acme-challenge` and `_acme-challenge.vm`, one for each name that needs it) | the NixOS module with the provider's token as a sops secret; `lego` follows the CNAME | **clean**: a documented ACME mechanism, no script; the token can obtain certificates for the delegated names |
| **2. Move the DNS hosting** (the nameservers) to a provider `lego` supports, keeping the current registrar | one change at the DNS provider; **every other record (mail: MX, SPF, DKIM) must be recreated at the new host** | clean, but the larger change |
| **3. Use the provider's API** through `lego`'s `exec` or `httpreq` provider with a small script | a script that talks to the provider's API, and a business API account at the provider | **glue**: an exception to enter in [the register](../exceptions.md) |
| **4. No DNS challenge**: HTTP-01 for the public names and **a private CA** for the VPN-only ones | a CA service (a small one) and its root trusted on every device | clean for the public names; one more service, and a root to install on each device |

**Recommendation: route 1.** It keeps the DNS provider as it is, adds no script and no service, and needs only a few CNAME records. **It has not been tried with a real provider**; when the owner agrees to open the free account (deSEC) it is tested, with route 4 as the fallback. **Caddy would need a plugin per provider** and the NixOS module and Traefik would not.
