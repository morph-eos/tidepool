# Register of exceptions to P1 (clean over clever)

Each entry is custom glue that is in the running system because no native way exists. An empty register is the goal; it holds thirteen entries.

| # | What it is | Why there is no native way | Who keeps it up to date | Test run at every upgrade | How it goes away |
|---|---|---|---|---|---|
| 1 | **pgBackRest with a local repository** ([ADR 0006](decisions/0006-postgresql-version-and-immich.md)): the two backup-job units of the module run as `postgres` (`User` and `Group` overridden with `mkForce`), `users.users.pgbackrest.homeMode = "770"`, `ReadWritePaths` of `postgresql.service` for the repository path, and the cipher passphrase in a file under pgBackRest's own `conf.d` (a sops-nix template in production; this last one is a documented pgBackRest feature, not glue) | the module is built for a repository on **another host**; pgBackRest creates directories 0750 whatever the umask, so the user that archives (`postgres`, inside a sandboxed unit) and the user of the jobs (`pgbackrest`) cannot both write; and the module refuses `cipher-pass` as an option (it would land in the world-readable Nix store) | me; the lines sit in `nixos/modules/database.nix` | after every nixpkgs update: the weekly job runs, `pgbackrest check` passes, and a point-in-time restore of a lab database succeeds (the lab bake-off script, and the restore drill of phase 7) | the module learns to run a local repository (or the repository moves to another host over SFTP); then the overrides are deleted |
| 2 | **The restore-test unit** ([ADR 0015](decisions/0015-backup-verification.md)): `pgbackrest-restore-test.service` and its timer in `nixos/modules/verify.nix`, about 20 lines of shell: `pgbackrest verify` (its report read, because it exits 0 on damage), a restore of the latest backup into a scratch folder with archiving off, a throwaway PostgreSQL on a Unix socket, `amcheck` and a count in each database, then removal | the pgBackRest module only schedules backups; no module restores into a scratch copy and checks it | me; the unit is in the flake | a lab run on the drill's data (`systemctl start pgbackrest-restore-test`, expect `success` and the assets counted); after every update of PostgreSQL or pgBackRest | pgBackRest or the module learns a restore-test job, or the check moves to a tool that does it natively |
| 3 | **The copy to Proton Drive** ([ADR 0007](decisions/0007-offsite-copy.md)): `nixos/modules/offsite.nix`: the official Proton Drive CLI pinned by URL and SHA-512 and run in an FHS environment with a throwaway D-Bus session and a keyring unlocked by a sops secret, and `proton-offsite-sync`, about 20 lines of shell (upload what is new, trash what the repository no longer has, under `borg with-lock`) | no module copies a Borg repository to Proton Drive; the CLI is a closed pre-1.0 binary that insists on a Secret Service; Hetzner Storage Box (a native Borg job) is the clean alternative and the fallback | me; the CLI's version is one line, bumped on purpose after the test | `lab/proton-offsite/` (an upload, a trash, a byte-for-byte restore and a `borg check --verify-data` of the copy); after every CLI version; the alert `ProtonOffsiteStale` and `UnitFailed` watch it in production | Proton ships a supported headless login or a Borg-aware sync, or the destination moves to the Storage Box and the module is deleted |
| 4 | **The single sign-on clients, and Jellyfin's plugin** ([ADR 0011](decisions/0011-services.md), [0020](decisions/0020-brand-identity.md)): `nixos/modules/sso.nix`, `nextcloud-oidc-clients.service`, about 12 lines of shell: for each declared client it compares Nextcloud's list (`occ oidc:list`) with the declaration and, if the secret or the redirect addresses differ, removes and creates the client (`occ oidc:remove`, `occ oidc:create`); and one nginx rule that answers the discovery document at the address Immich asks; and for Jellyfin, `nixos/jellyfin/sso/sso-config.sh` (shell and a few lines of Perl), which before each start puts the sign-in plugin from a pinned zip in place when none is installed and writes four fields of its settings file in place (endpoint, client id, secret, enabled flag) | the oidc app has no declarative setting for its clients, only commands; Immich's OpenID library does not follow the redirect Nextcloud puts on `/.well-known/openid-configuration`; Jellyfin's plugin has no declarative setting, only a settings file that it rewrites itself (the links between users are kept in it), and it is not in nixpkgs | me; the lines are in the flake | `lab/gate.sh` (steps `brand` and `smoke`: the login from Immich through Nextcloud, in a browser; the client registered; Immich starting on its file); the CI's `brand` check holds the client id's constraints and runs the script on a temporary directory (writes, leaves a differing provider alone, adopts four fields and keeps the links); `lab/brand-test.sh` (the plugin, its settings and the button on a Jellyfin that started); after every update of Nextcloud's oidc app or Immich | the oidc app gets a declarative client setting, or Immich follows the redirect; the plugin gets a declarative setting or Jellyfin its own single sign-on |
| 5 | **The brand in Nextcloud** ([ADR 0020](decisions/0020-brand-identity.md)): `nextcloud-brand.service` in `nixos/modules/brand.nix`, seven `occ theming:config` commands | Nextcloud's theming lives in its database, set by commands | me | `lab/gate.sh` (step `brand`: the login page's name and logo); after every update of Nextcloud | Nextcloud reads its theming from a file |
| 6 | **Jellyfin's served web config** ([ADR 0020](decisions/0020-brand-identity.md)): the image's own `config.json` (copied in `nixos/brand/jellyfin-web-config.json`) is served instead of the image's, with the brand's theme added as the default and a `theme.css` mounted next to the built-in themes | Jellyfin Web takes its themes from that file and has no setting to add one | me; the copy is refreshed when the image's digest changes | `lab/gate.sh` (step `brand`): it compares the served file with the pinned image's and fails if they differ by more than the themes; the CI's `brand` check holds the file's shape | Jellyfin takes a default theme from a setting, or the brand is dropped (`tidepool.brand.enable = false`) |
| 7 | **The alert of a failed service** ([ADR 0012](decisions/0012-observability.md)): `tidepool-alert@.service` in `nixos/modules/observability.nix`, a few lines of shell (`jq` and `curl`) that post a `BackupJobFailed` or `ServiceFailed` alert to Alertmanager's API, started by the `OnFailure=` that a drop-in for all services puts on every service | `UnitFailed` reads a failed state that a switch of the deploy can clear before a scrape sees it, and no timer rule tells a job that ran and failed from one that succeeded; the Prometheus module has no rule for "the unit failed once" | me | `lab/smoke-test.sh` (a failing service reaches the mail sink; the alert unit has no alert of its own); the first failure on the real host | Prometheus or Alertmanager gain a notification for a unit's failure, or a "last success" metric replaces it |
| 8 | **The last success of a backup unit** ([ADR 0012](decisions/0012-observability.md)): `tidepool-stamp-success` in `nixos/modules/observability.nix`, three lines of shell run by `ExecStopPost=` of each backup unit, that write the time of a successful run into a textfile of the node exporter, read by the rule `BackupNoRecentSuccess` | the node exporter's systemd collector knows when a timer fired and whether a unit is failed, not when it last ended well; the Prometheus module has no such metric | me | `lab/smoke-test.sh` (the dump unit leaves a recent time; the versions' metrics are still read from the same directory); the first real run of each unit | systemd or the node exporter gain a "last successful run" metric for units |
| 9 | **Floppy's palette, title and logo** ([ADR 0020](decisions/0020-brand-identity.md), [0023](decisions/0023-floppy.md)): the edge adds one stylesheet (`/_brand/theme.css`, made by `nixos/modules/brand.nix` from the brand's colours) to Floppy's pages with `sub_filter`: every colour variable `!important` (the palette, and Tailwind's indigo scale that its buttons and borders use) and its logo replaced by the brand's; and the same filter gives the page's title and the installed app's name the brand's name of the service ("<name> <label>") in place of Floppy's own; written in `nixos/modules/floppy.nix` | Floppy keeps its colours as a theme per user in its database: there is no setting that gives every user, and the sign-in page before any user exists, one palette; its title and app name are in its templates, with no setting | me | the CI's `brand` check (the palette reaches the stylesheet, the title rewrite carries the brand's name of the service, a brand file of another repository changes it, the brand off adds nothing, the text keeps WCAG AA contrast on every surface); `lab/brand-test.sh` and `lab/sso-check.py` (the stylesheet is served, the page links it, the browser computes the brand's accent on Floppy's sign-in page, and its tab says the service's name) | Floppy takes a palette from a setting of the server, or the brand is dropped (`tidepool.brand.enable = false` leaves the pages as they come) |
| 10 | **Nextcloud's footer** ([ADR 0020](decisions/0020-brand-identity.md)): `nixos/modules/brand.nix` adds one `sub_filter` to Nextcloud's virtual host that turns the footer's link text "<name> <cloud>" ("Tidepool Cloud") back into the brand's name ("Tidepool"), so that the footer reads "Tidepool – your own cloud" while the page, the tab and the app are "Tidepool Cloud"; only when the two differ | Nextcloud's theming has one field for the name of the page, the tab and the footer's entity: the footer repeats it before the tagline | me | the CI's `brand` check (the rewrite is there for a brand of another repository and absent when the names do not differ); `lab/brand-test.sh` and `lab/brand-check.py` (the login page's footer says the brand's name and the tagline, and its tab the service's name) after every update of Nextcloud | Nextcloud's theming gets a field for the footer's name, or the brand's labels are left empty |
| 11 | **Immich's tab title** ([ADR 0020](decisions/0020-brand-identity.md)): `nixos/modules/brand.nix` adds one `sub_filter` to Immich's virtual host, on the one chunk of its web client that writes the title (`nodes/0.<hash>.js`), turning `<page> - Immich` into `<page> - <name of the service>` | Immich writes the title in the browser, in its own code, and has no setting for it | me | the CI's `brand` check (the rewrite is there, with the brand's name of the service, for the default brand and another repository's); `lab/brand-check.py` and `lab/brand-alt.py` (the tab says the service's name) after every update of Immich | Immich gets a setting for its title, or the brand's `photos` label is left empty (the title then says the brand's name alone) |
| 12 | **The favicons and app icons of Immich, Jellyfin and Floppy** ([ADR 0020](decisions/0020-brand-identity.md)): `nixos/modules/brand.nix` builds the sizes the programs use (16 to 512 px and a `favicon.ico`) from the brand's mark with `rsvg-convert` and ImageMagick, at build time, and the edge serves them at the paths where each program has its own (exact locations for Immich's and Floppy's, a pattern for Jellyfin's hashed names); the interface's own logos in Immich are replaced by the stylesheet in its settings | None of the three has a setting for its favicon or its app icons: they are files of the image | me | the CI's `brand` check (the locations exist for the default brand, another repository's brand builds its own set, the brand off leaves them out); `lab/brand-check.py` (each icon is the brand's, not the program's) after every update of Immich, Jellyfin or Floppy | a program gets a setting for its icons, or its icon files are no longer at those paths (the check says so) |
| 13 | **The weekly fill of timed lyrics** ([ADR 0023](decisions/0023-floppy.md)): `nixos/modules/jellyfin-lyrics.nix`, one oneshot unit and its timer that run `nixos/jellyfin/lyrics/lrc_fill.py` (standard-library Python and `ffprobe`) over the music folders named in `tidepool.services.jellyfin.lyrics.directories`, as a user who can write there | The media mounts are read-only for Jellyfin's container, so its own lyrics plugin cannot leave a sidecar file; nothing native keeps a library's `.lrc` files up to date from a free service | me | `nix flake check` evaluates the unit and arms its timer on the lab host; the script's rules (fill, upgrade a plain file, leave a timed one, mark an instrumental, a second run does nothing) were tried on a made-up library with the service replaced | goes away if Jellyfin stores the lyrics it fetches, or if its mounts are writable and the plugin writes sidecars |

**Planned and not yet in the system:** nothing.

Rules: an entry is added **in the same commit** as the glue; a phase does not close with an entry that has no test; when a native way appears the entry is removed and the glue deleted.
