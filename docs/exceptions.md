# Register of exceptions to P1 (clean over clever)

Each entry is custom glue that is in the running system because no native way exists. An empty register is the goal; it holds six entries.

| # | What it is | Why there is no native way | Who keeps it up to date | Test run at every upgrade | How it goes away |
|---|---|---|---|---|---|
| 1 | **pgBackRest with a local repository** ([ADR 0006](decisions/0006-postgresql-version-and-immich.md)): the two backup-job units of the module run as `postgres` (`User` and `Group` overridden with `mkForce`), `users.users.pgbackrest.homeMode = "770"`, `ReadWritePaths` of `postgresql.service` for the repository path, and the cipher passphrase in a file under pgBackRest's own `conf.d` (a sops-nix template in production; this last one is a documented pgBackRest feature, not glue) | the module is built for a repository on **another host**; pgBackRest creates directories 0750 whatever the umask, so the user that archives (`postgres`, inside a sandboxed unit) and the user of the jobs (`pgbackrest`) cannot both write; and the module refuses `cipher-pass` as an option (it would land in the world-readable Nix store) | the owner and the assistant; the lines sit in `nixos/modules/database.nix` | after every nixpkgs update: the weekly job runs, `pgbackrest check` passes, and a point-in-time restore of a lab database succeeds (the lab bake-off script, and the restore drill of phase 7) | the module learns to run a local repository (or the repository moves to another host over SFTP); then the overrides are deleted |
| 2 | **The restore-test unit** ([ADR 0015](decisions/0015-backup-verification.md)): `pgbackrest-restore-test.service` and its timer in `nixos/modules/verify.nix`, about 20 lines of shell: `pgbackrest verify` (its report read, because it exits 0 on damage), a restore of the latest backup into a scratch folder with archiving off, a throwaway PostgreSQL on a Unix socket, `amcheck` and a count in each database, then removal | the pgBackRest module only schedules backups; no module restores into a scratch copy and checks it | the owner and the assistant; the unit is in the flake | a lab run on the drill's data (`systemctl start pgbackrest-restore-test`, expect `success` and the assets counted); after every update of PostgreSQL or pgBackRest | pgBackRest or the module learns a restore-test job, or the check moves to a tool that does it natively |
| 3 | **The copy to Proton Drive** ([ADR 0007](decisions/0007-offsite-copy.md)): `nixos/modules/offsite.nix`: the official Proton Drive CLI pinned by URL and SHA-512 and run in an FHS environment with a throwaway D-Bus session and a keyring unlocked by a sops secret, and `proton-offsite-sync`, about 20 lines of shell (upload what is new, trash what the repository no longer has, under `borg with-lock`) | no module copies a Borg repository to Proton Drive; the CLI is a closed pre-1.0 binary that insists on a Secret Service; Hetzner Storage Box (a native Borg job) is the clean alternative and the fallback | the owner and the assistant; the CLI's version is one line, bumped on purpose after the test | `lab/proton-offsite/` (an upload, a trash, a byte-for-byte restore and a `borg check --verify-data` of the copy); after every CLI version; the alert `ProtonOffsiteStale` and `UnitFailed` watch it in production | Proton ships a supported headless login or a Borg-aware sync, or the destination moves to the Storage Box and the module is deleted |
| 4 | **The single sign-on clients** ([ADR 0011](decisions/0011-services.md), [0020](decisions/0020-brand-identity.md)): `nixos/modules/sso.nix`, `nextcloud-oidc-clients.service`, about 12 lines of shell: for each declared client it compares Nextcloud's list (`occ oidc:list`) with the declaration and, if the secret or the redirect addresses differ, removes and creates the client (`occ oidc:remove`, `occ oidc:create`); and one nginx rule that answers the discovery document at the address Immich asks | the oidc app has no declarative setting for its clients, only commands; Immich's OpenID library does not follow the redirect Nextcloud puts on `/.well-known/openid-configuration` | the owner and the assistant; the lines are in the flake | `lab/gate.sh` (steps `brand` and `smoke`: the login from Immich through Nextcloud, in a browser; the client registered; Immich starting on its file); the CI's `brand` check holds the client id's constraints; after every update of Nextcloud's oidc app or Immich | the oidc app gets a declarative client setting, or Immich follows the redirect |
| 5 | **The brand in Nextcloud** ([ADR 0020](decisions/0020-brand-identity.md)): `nextcloud-brand.service` in `nixos/modules/brand.nix`, seven `occ theming:config` commands | Nextcloud's theming lives in its database, set by commands | the owner and the assistant | `lab/gate.sh` (step `brand`: the login page's name and logo); after every update of Nextcloud | Nextcloud reads its theming from a file |
| 6 | **Jellyfin's served web config** ([ADR 0020](decisions/0020-brand-identity.md)): the image's own `config.json` (copied in `nixos/brand/jellyfin-web-config.json`) is served instead of the image's, with the brand's theme added as the default and a `theme.css` mounted next to the built-in themes | Jellyfin Web takes its themes from that file and has no setting to add one | the owner and the assistant; the copy is refreshed when the image's digest changes | `lab/gate.sh` (step `brand`): it compares the served file with the pinned image's and fails if they differ by more than the themes; the CI's `brand` check holds the file's shape | Jellyfin takes a default theme from a setting, or the brand is dropped (`tidepool.brand.enable = false`) |

**Planned and not yet in the system:** nothing.

Rules: an entry is added **in the same commit** as the glue; a phase does not close with an entry that has no test; when a native way appears the entry is removed and the glue deleted.
